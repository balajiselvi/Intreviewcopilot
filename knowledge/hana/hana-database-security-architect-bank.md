# SAP HANA Database & Data-Platform Security Architecture

Spoken architect style: Decision → Mechanism → Governance → Validation.

**Product boundaries:** HANA users/roles/privileges (SQL + repository/XSA where applicable) are the database plane. They are **not** PFCG roles and **not** BW analysis authorizations—though BW/SAC/S/4 may sit above and depend on HANA privileges for technical connectivity. Distinguish classic HANA repository vs HDI/XSA patterns by release.

**Anti-surface rule:** Prefer system/object/analytic privileges, schema design, audit policies, and technical-user least privilege over “HANA has roles.”

## Q1: How do you separate database administration privileges from application schema access?

- **Decision:** DBA roles (system management, user admin, backup) are isolated from application runtime users that only need schema object privileges.
- **Mechanism:** Create least-privilege application users/roles with SELECT/EXECUTE on required schemas/objects; grant DATA ADMIN / USER ADMIN only to named DBA groups. Prefer roles over direct privilege grants to users. For HDI, use container technical users generated by deployment—do not share `_SYS_REPO`-style god users with developers in Production.
- **Governance:** Production DBA access via PAM/break-glass with logging. Quarterly review of system privilege holders.
- **Validation:** App user cannot create users; DBA can; app works with object privileges only; `EFFECTIVE_PRIVILEGES` / role query shows expected set.

## Q2: How do you design analytic privileges / data-level authorization for calculation views?

- **Decision:** Analytic privileges (or equivalent structured filters) restrict row-level analytic access for reporting users—complementary to SAC DAC / BW analysis auth when those tools are front-ends.
- **Mechanism:** Define analytic privilege on relevant attributes (e.g., company code); assign to HANA roles used by reporting users or SSO-mapped users. For HDI, package analytic privileges with containers. Document whether enforcement is HANA-side, tool-side, or both (ADR).
- **Governance:** Dual maintenance without ADR rejected. `0BI_ALL`-style “full data” HANA roles banned for business users.
- **Validation:** User without member sees filtered/empty result; explain plan / auth trace (release tools) confirms filter; SAC live user cannot bypass via DB login.

## Q3: How do you manage technical users for S/4, BW, SAC, and middleware connectivity?

- **Decision:** One purpose per technical user (replication, ETL, live connect, app runtime)—no shared “HANA_INTEGRATION” superuser.
- **Mechanism:** Create users with schema-scoped privileges; store passwords in CyberArk/secret store; prefer X.509 where supported; rotate and update destinations (`DBCO`, SAC connection, SDI). Restrict `RESTRICTED` user flags as designed.
- **Governance:** Password in config files is incident. Ownership in CMDB per technical user.
- **Validation:** Connection test succeeds; privilege fail when schema revoked; rotation test updates secret; audit shows technical user only from expected hosts if network policy allows.

## Q4: How do you implement HANA audit logging for privileged and sensitive access?

- **Decision:** Audit policies cover user admin, privilege grants, sensitive schema SELECTs, and failed authentications—retained per compliance.
- **Mechanism:** Create audit policies (e.g., actions on `GRANT`, `CREATE USER`, SELECT on PII schema); enable audit trail (table/firewall/syslog per design); monitor growth and ship to SIEM. Protect audit trail from tampering (separate admin).
- **Governance:** Disable of audit policies requires CAB. SOX-relevant schemas explicitly listed.
- **Validation:** Controlled GRANT appears in audit; SELECT on sensitive table logged; SIEM alert fires in non-prod test; policy status active.

## Q5: How do you enforce encryption and secure communication for HANA?

- **Decision:** TLS for client/server communications and encryption of data at rest per enterprise crypto standards—no cleartext Production JDBC from uncontrolled networks.
- **Mechanism:** Configure SSL/TLS with enterprise certificates; enforce secure connectors from S/4/SAC/middleware; manage PSE/certificate stores; encrypt disk/backup per operations standard. Rotate certificates before expiry.
- **Governance:** Certificate calendar owned by Platform + Security. Exception for non-TLS only in isolated non-prod with risk acceptance.
- **Validation:** Client forced to TLS succeeds; non-TLS attempt fails; certificate expiry monitor green; vulnerability scan clear for cleartext DB ports from untrusted zones.

## Q6: How do you authorize XSA / HDI developers versus Production deployment?

- **Decision:** Developers deploy to DEV spaces; Production deployment is pipeline-owned with separate runtime users—no standing Production space developer.
- **Mechanism:** Space/org roles in XSA; HDI container deploy via CI with technical deployer user; runtime users get only execute/select as needed. Bind services least privilege.
- **Governance:** Production space Developer role = finding. Pipeline secrets in vault.
- **Validation:** Developer cannot deploy to Prod space; pipeline deploy succeeds; runtime user lacks deploy privilege.

## Q7: How do you troubleshoot authorization failures at the HANA layer versus application layer?

- **Decision:** Confirm which layer denied: app session (S/4/BW/SAC) vs HANA privilege vs network/TLS.
- **Mechanism:** Reproduce with DB user; query effective privileges; check analytic privilege; review audit trail for DENY; validate SAC/BW user mapping to HANA user. Distinguishing “empty data” (analytic filter) from SQL error (missing SELECT).
- **Governance:** Fix least privilege at correct layer; ban granting DATA ADMIN to clear app errors.
- **Validation:** Grant minimal object privilege → success; control user still denied; ticket cites privilege name.

## Q8: How do you integrate HANA security with BW/4 and SAC live scenarios?

- **Decision:** Declare enforcement: BW analysis auth for BW-managed providers; HANA analytic privileges for HANA-live views; SAC DAC as additional UX control—not a replacement for backend.
- **Mechanism:** Document connection user vs SSO passthrough; align attribute semantics (company code) across tools; test deny at each layer. Avoid granting broad `_SYS_BI` access to business users.
- **Governance:** ADR per data product. Cross-team change (BW auth + HANA privilege) in one CR when interdependent.
- **Validation:** Deny matrix: BW deny, HANA deny, SAC DAC deny each proven; success path least privilege only.

## Q9: How do you govern privileged HANA access with PAM / CyberArk?

- **Decision:** Interactive DBA accounts are checked out via PAM with session recording where feasible; application secrets via CCP—not shared DBA passwords.
- **Mechanism:** Vault HANA SYSTEM/DBA equivalents; CPM rotate where supported; brokers sessions; alert PTA/SIEM on anomalous DB admin. App passwords rotated with destination update runbook.
- **Governance:** Standing shared SYSTEM password banned. Checkout requires ticket for Production.
- **Validation:** Checkout works; rotation updates; direct shared password login disabled; session evidence retained.

## Q10: What audit evidence pack do you require for HANA security?

- **Decision:** Evidence includes privilege inventory, audit policy config, technical user roster, encryption/TLS status, and break-glass logs.
- **Mechanism:** Export role/privilege reports; admin user list; audit policy definitions; connection inventory; PAM checkout samples; vulnerability scan summary.
- **Governance:** Deploy/ops gate for material changes requires Security review of privilege deltas.
- **Validation:** Walkthrough: least-privilege app user; DBA via PAM; audit event present; analytic deny proven.
