# SU24

## Overview

SU24 maintains the authorization default proposals for transactions — it's the table-driven engine that tells PFCG which authorization objects and field values to propose when a transaction is added to a role's menu. Without accurate SU24 data, role building becomes a manual, error-prone process for every single transaction.

## Interview Summary

SU24 links transactions to the authorization objects they typically need, with default field values. When you add a transaction to a role in PFCG, it's SU24 that supplies the starting authorization data. Keeping SU24 accurate, especially for custom Z-transactions, is what makes role building fast and consistent instead of manual guesswork.

## 60 Second Interview Answer

SU24 is the default-value engine behind PFCG's authorization tab. Every standard SAP transaction has entries in SU24 that say which authorization objects it typically checks and what field values usually apply. When a role builder adds that transaction to a role's menu, PFCG queries SU24 and proposes those objects and values automatically.

This matters most for custom development. Standard transactions come with SU24 data out of the box, but a custom Z-transaction has none unless someone maintains it. Without SU24 entries, the role builder either gets no authorization proposal at all — meaning they have to know and add every object manually — or worse, the transaction only ends up protected by S_TCODE with no deeper authorization check at all.

Keeping SU24 accurate as custom development happens is a recurring maintenance responsibility, not a one-time setup task. Every new Z-transaction or modified standard transaction needs its SU24 entries reviewed.

## 90 Second Interview Answer

SU24 is the table-driven default-proposal engine that sits behind PFCG's authorization tab. Every transaction in the system can have SU24 entries describing which authorization objects it typically requires and what default field values usually apply — activity codes, authorization groups, and so on. When a role builder adds that transaction to a role's menu, SU24 is queried automatically and the proposed objects populate the authorization tab as a starting point.

The practical impact shows up most clearly with custom development. Standard SAP transactions ship with SU24 data already maintained, so role building for standard functionality is mostly a matter of reviewing and tightening proposed values. Custom Z-transactions have none of that by default — if a developer builds a new transaction and nobody maintains its SU24 entries, the role builder adding that transaction to a role either gets zero authorization proposals, meaning they have to know exactly which objects to add manually, or the transaction ends up with no meaningful authorization check beyond S_TCODE at all, which is a real security gap disguised as a convenience.

SU24 maintenance is also why role catalogs can drift after custom development picks up pace. If ten Z-transactions get built over a project without corresponding SU24 maintenance, every future role builder touching those transactions is starting from nothing, and the resulting authorization data ends up inconsistent from role to role because everyone is guessing independently instead of working from a shared default.

The other place SU24 matters is upgrades. SAP periodically changes its own default proposals for standard transactions, and reconciling those changes against what's already live in your roles is exactly what SU25 handles — SU24 is the data, SU25 is the process for absorbing changes to that data safely.

## Architecture

- SU24 entries: transaction-to-authorization-object mappings with default field values
- Standard transaction defaults: shipped by SAP, maintained by SAP notes and support packages
- Custom transaction defaults: must be manually maintained for Z-transactions
- Proposal type: check, no-check, or maintain flags controlling how PFCG treats the object
- Relationship to PFCG: the direct data source for the authorization tab's initial proposals

## Runtime Flow

SU24 has no runtime role itself — it doesn't get checked when a user executes a transaction. Its role is entirely at role-build time: when a transaction is added to a role's menu in PFCG, the system looks up SU24 entries for that transaction and populates the authorization tab with the proposed objects and values. Those become part of the role's authorization data once maintained and generated, and it's the generated profile, not SU24, that gets checked at runtime.

## Configuration

- Maintain SU24 entries for every custom Z-transaction as part of development
- Review and correct default field values that don't fit the actual business process
- Set the proposal type correctly — check, no-check, or maintain — for each object
- Periodically reconcile SU24 data after support packages or upgrades via SU25

## Implementation Activities

- Review SU24 proposals for standard transactions in scope for the project
- Build SU24 entries for every new custom Z-transaction

## Migration Activities

- Compare SU24 data between source and target systems during an upgrade
- Reconcile changed SAP default proposals through the SU25 process
- Validate custom transaction SU24 entries transported correctly

## Rollout Activities

- Confirm SU24 data for transactions used by the rollout entity is complete and accurate
- Extend SU24 entries for any new custom transactions built specifically for the rollout
- Re-test role building against SU24 proposals in the new environment

## Production Support Activities

- Investigate role building issues caused by missing or incorrect SU24 data
- Maintain SU24 entries as new custom transactions are deployed
- Support root cause analysis when a transaction has inconsistent authorization behavior across roles

## Troubleshooting

Common issue: a custom transaction gets added to a role but no authorization objects are proposed.
Root cause: SU24 was never maintained for that transaction.
Resolution: build the SU24 entry with the correct authorization objects and default values, then rebuild the role's authorization data.

Common issue: different roles end up with inconsistent authorization values for the same custom transaction.
Root cause: no SU24 defaults existed, so each role builder added objects manually with their own guesses.
Resolution: create proper SU24 entries and standardize existing roles against the new defaults.

Common issue: a transaction proposes an authorization object that doesn't actually apply to how the business uses it.
Root cause: outdated or incorrect SU24 data.
Resolution: correct the SU24 entry, then review and rebuild affected roles.
