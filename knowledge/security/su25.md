# SU25

## Overview

SU25 is the guided process for reconciling SU24 authorization default changes after an SAP upgrade or support package. It walks through a series of steps that compare what SAP shipped as new defaults against what's already live in your roles, so you can absorb changes safely without silently breaking or over-granting existing access.

## Interview Summary

Every upgrade or major support package can change SAP's own SU24 default proposals. SU25 is the structured process for reviewing those changes, deciding which ones to accept, and regenerating affected roles. Skipping SU25 after an upgrade means your roles are built against stale authorization defaults that no longer match what SAP actually ships.

## 60 Second Interview Answer

SU25 is a guided, step-based process specifically for upgrade and support package scenarios. When SAP ships a new release, the standard SU24 authorization default proposals often change — new objects get added to transactions, field values get adjusted, sometimes objects get deprecated entirely.

SU25 walks through comparing the new SAP-delivered defaults against your customer-specific SU24 modifications and against what's currently live in your roles. It's not a single action, it's a sequence of steps that lets you selectively accept new defaults, preserve your customizations where they still apply, and flag transactions that need review.

Skipping SU25 after an upgrade is a common mistake, and the consequence is roles built against stale authorization data. New transactions or new authorization requirements on existing transactions won't be reflected, and you end up with a mismatch between what SAP expects and what your roles actually enforce, sometimes discovered only when users hit authorization errors on things that used to work.

## 90 Second Interview Answer

SU25 is the structured, step-based process for reconciling SU24 authorization default changes specifically in upgrade and support package scenarios. It exists because SAP periodically revises its own standard proposals — adding new authorization objects to existing transactions, adjusting default field values, or deprecating objects that no longer apply — and those changes need to be deliberately absorbed, not silently ignored.

The process works through a defined sequence of steps: comparing the newly delivered SAP defaults against any customer-specific modifications already made to SU24, and against what's currently reflected in live roles. At each step you're making a decision about whether to accept the new SAP default, preserve an existing customization, or flag something for manual review. This matters because a blind accept-everything approach can silently loosen or break existing authorization behavior, while ignoring SU25 entirely leaves your role catalog running on stale defaults that no longer match the upgraded system.

The practical consequence of skipping SU25 shows up gradually rather than immediately. Existing roles keep working in the short term because they were already generated against the old defaults. The problem surfaces when someone builds a new role or modifies an existing one after the upgrade — they're now working from outdated SU24 data, and the resulting role doesn't reflect what the upgraded system actually needs. Sometimes this only gets discovered when a user hits an authorization error on a transaction that has new requirements the role was never updated to include.

The other reason SU25 matters operationally is that it's the trigger point for a mass role regeneration exercise. After working through SU25 and accepting the relevant changes, the standard follow-up is regenerating affected roles across the catalog, which is itself a coordinated activity that needs planning, not something to run casually against production.

## Architecture

- SU25 step sequence: the guided workflow for reconciling SU24 changes
- New SAP-delivered defaults: what changes with each upgrade or support package
- Customer-specific SU24 modifications: existing customizations that may or may not still apply
- Comparison and decision points: where you accept, preserve, or flag each change
- Downstream role regeneration: the follow-up activity after SU25 completes

## Runtime Flow

SU25 has no runtime component — like SU24, it's entirely a design-time and upgrade-time process. Its output is updated SU24 data, which then feeds into future PFCG role building the same way any SU24 data does. The actual runtime AUTHORITY-CHECK behavior only changes once affected roles are regenerated after SU25 completes.

## Configuration

- Run SU25 as a mandatory step after every SAP upgrade or significant support package
- Work through each step deliberately rather than accepting all changes by default
- Document decisions made at each step for future audit and reference
- Plan and schedule the follow-up mass role regeneration after SU25 completes

## Implementation Activities

- Schedule SU25 execution as part of the upgrade project plan
- Review and decide on each proposed SU24 change during the SU25 steps
- Coordinate mass role regeneration after SU25 decisions are finalized
- Test affected roles in a non-production environment before deploying the regeneration to production

## Migration Activities

- Run SU25 immediately following any system upgrade or migration that touches the SAP release level
- Compare pre- and post-upgrade SU24 data to understand the scope of change
- Validate that customer-specific SU24 modifications were correctly preserved or reconciled

## Rollout Activities

- Confirm SU25 has already been completed on the source system template before extending roles to a new rollout entity
- Avoid re-running SU25 unnecessarily for a rollout that doesn't involve a system upgrade

## Production Support Activities

- Investigate authorization errors that trace back to skipped or incomplete SU25 reconciliation
- Support planning for the next upgrade's SU25 exercise
- Maintain documentation of past SU25 decisions for audit purposes

## Troubleshooting

Common issue: a transaction that worked before an upgrade now throws an authorization error.
Root cause: SU25 wasn't run, or was run but the relevant change wasn't accepted, leaving the role missing a newly required authorization object.
Resolution: run or complete SU25 for the affected transaction, accept the relevant change, and regenerate the role.

Common issue: SU25 was run and accepted broadly, and now some roles have unexpectedly different authorization values.
Root cause: accepting all new defaults without review can overwrite customer-specific SU24 modifications that were intentional.
Resolution: review which customizations were lost, restore them deliberately in SU24, and regenerate affected roles.

Common issue: roles built after an upgrade are inconsistent with roles built before it.
Root cause: SU25 reconciliation happened partway through a project, so some roles reflect old defaults and others reflect new ones.
Resolution: complete SU25 fully, then regenerate the entire affected role set consistently.

## Best Practices

- Treat SU25 as a mandatory, scheduled step in every upgrade project, not an optional cleanup task
- Review and decide on changes deliberately rather than accepting all new defaults blindly
- Document every decision made during SU25 for future audit and reference
- Test role regeneration in a non-production environment before deploying broadly
- Complete SU25 fully rather than stopping partway through the step sequence

## Common Mistakes

- Skipping SU25 entirely after an upgrade or support package
- Accepting all SU25 changes without reviewing their impact on customizations
- Stopping SU25 partway through, leaving inconsistent authorization data across the role catalog
- Not scheduling the follow-up mass role regeneration after SU25 completes
- Treating SU25 as purely a Basis activity with no security review

## Interviewer's Hidden Expectations

Interviewers want to hear that you treat SU25 as a critical, scheduled part of the upgrade lifecycle, not an afterthought. They're listening for whether you understand the gradual, sometimes-delayed way skipped SU25 reconciliation actually surfaces as production issues.

## What Makes This a 10/10 Answer

An average answer says SU25 reconciles SU24 changes after an upgrade. A 10/10 answer explains the step-based decision process, the risk of both skipping it and blindly accepting everything, and the downstream mass role regeneration that has to follow it.

## Red Flags

- Not mentioning the risk of skipping SU25 after an upgrade
- Suggesting all SU25 changes should always be accepted without review
- No mention of the follow-up role regeneration activity
- Treating SU25 as a one-time historical activity rather than a recurring upgrade step
