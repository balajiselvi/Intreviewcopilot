# SAP GRC Access Control — Connector Supplemental Q&A\n\nSupplemental spoken answers for Access Control connectors. IDs SAPSUP-001..010. Top-100 IDs unchanged.\n\n## SAPSUP-001: What is a connector in SAP GRC Access Control?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** concept  \n**Verification:** internally_reviewed_with_help_portal_references\n\n**Answer:** An SAP GRC Access Control connector is the logical configuration that identifies a governed source or target system and how Access Control communicates with it for enabled scenarios such as authorization data synchronization, access-risk analysis, role management and—when provisioning is configured—assignment changes. For an ABAP system the communication path commonly uses an SM59 RFC destination and a dedicated communication user; in GRC I confirm the connector name, connection type, connector group, Integration Framework connection settings and Access Control connector settings for the landscape. I grant only the authorizations required for the enabled operations: read and extraction for synchronization and risk analysis is not automatically the same privilege set needed to create or change assignments. I then test connectivity, run the appropriate synchronization, reconcile counts and sample records against the target, run ARA against a known test case, and test provisioning separately if enabled. If the landscape routes provisioning through SAP IDM or another integration, I validate that complete path rather than assuming Access Control writes directly to every target. Exact configuration and permissions depend on the Access Control release, connector type and architecture.\n\n**Aliases:** What is an SAP GRC connector?; SAP GRC connector definition; explain GRC Access Control connector; what is a GRC connector\n\n**Must include:** logical configuration for source or target; enabled scenarios not assumed universal; least privilege by function; connectivity then sync then ARA then provisioning separately; release and architecture dependency\n\n**Must not:** one universal technical-user authorization set; all non-SAP targets use one generic REST connector; confusing IAG with Access Control Integration Framework; claiming GRACCONNECTORS as a verified transaction\n\n**Sources:**\n- Integration: SAP Access Control with SAP SuccessFactors (Integration Framework connector setup): https://help.sap.com/doc/2b63cae4868f406f9e5b5270be6bc30b/12.0.32/en-US/loio4d394fdcd0634b19a26b0b754c4eb7e0_EN.pdf — Documents Create Connectors, Maintain Connectors and Connection Types, Maintain Connection Settings (PROV/AUTH/ROLMG), Maintain Connector Settings, Maintain Mapping for Actions and Connector Groups. SuccessFactors example uses HTTP Type G; do not copy SF connection type onto ABAP RFC targets.\n- KBA 2511548 — Integration Scenarios to Connector link: https://userapps.support.sap.com/sap/support/knowledge/en/2511548 — Access Control 10.0/10.1/12.0 scenario-to-connector relationships including Portal and LDAP.\n\n## SAPSUP-002: What is the difference between a source connector and a target connector in SAP GRC Access Control?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** comparison  \n**Verification:** internally_reviewed_with_help_portal_references\n\n**Answer:** In Access Control I separate purpose from technology. A source-oriented connector is used where GRC reads identity or authorization data into repository and analysis processes. A target-oriented connector is used where GRC sends or applies changes—most commonly provisioning after an approved access request—or where the system is the governed endpoint for risk and role scenarios. The same physical system often appears as one connector that is linked to multiple integration scenarios such as AUTH, ROLMG and PROV, so “source versus target” is about which scenarios and actions are enabled, not two unrelated products. I confirm connector group mapping for actions such as role risk analysis versus provisioning, keep the communication user least-privileged for those actions, and validate read paths separately from write paths. I do not treat a successful RFC ping as proof that both synchronization and provisioning work.\n\n**Aliases:** Explain source vs target connectors in GRC; source connector versus target connector GRC; GRC source and target connector difference\n\n**Must include:** purpose versus technology; scenarios AUTH ROLMG PROV; same system may serve multiple scenarios; validate read and write separately\n\n**Must not:** implying source and target are always different RFC destinations; IAG RequestTypeRule as Access Control connector setup\n\n**Sources:**\n- Integration Framework — Maintain Connection Settings / action mapping: https://help.sap.com/doc/2b63cae4868f406f9e5b5270be6bc30b/12.0.32/en-US/loio4d394fdcd0634b19a26b0b754c4eb7e0_EN.pdf — Scenario-connector link and action mapping (e.g. 0002 Role Risk Analysis, 0004 Provisioning) show purpose is configuration-driven.\n\n## SAPSUP-003: How do you configure and validate a connector in SAP GRC Access Control 10.x or 12.x?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** implementation  \n**Verification:** internally_reviewed_with_help_portal_references\n\n**Answer:** I separate connection setup from Access Control functional enablement. First I create or confirm the technical destination—for ABAP targets an SM59 RFC destination; for HTTP/cloud targets the documented HTTP connection type for that application—and prove basic connectivity. In SPRO under Governance, Risk and Compliance, Common Components, Integration Framework I maintain connectors and connection types, assign the connector to a connector group, and maintain connection settings so the connector is linked to the required integration scenarios such as AUTH, ROLMG and PROV. Then in Access Control customizing I maintain connector settings and map actions to connector groups, and I activate the connector group only when the mapping is complete. Validation is staged: destination test, connector registration check, repository or authorization synchronization for a controlled sample, ARA against a known conflict and a known clean user, and a separate provisioning test if PROV is in scope. Exact IMG nodes and application types are release- and connector-type specific, so I confirm them on the system and in the Access Control integration guide for that release rather than memorizing one universal path.\n\n**Aliases:** How do you configure and test an SAP GRC connector?; How do I configure/test an SAP GRC connector?; configure GRC Access Control connector; GRC Integration Framework connector setup\n\n**Must include:** destination before Integration Framework registration; connector group and scenario link; Access Control action mapping; staged validation sync ARA provision; release-specific confirmation\n\n**Must not:** GRFNMW_CONFIG as connector setup; GRAC_SPM as connector setup; invented transaction GRACCONNECTORS\n\n**Sources:**\n- Integration Framework connector setup (Create Connectors / Maintain Connectors and Connection Types / Maintain Connection Settings): https://help.sap.com/doc/2b63cae4868f406f9e5b5270be6bc30b/12.0.32/en-US/loio4d394fdcd0634b19a26b0b754c4eb7e0_EN.pdf — 12.0.x Help integration guide; worked example is SuccessFactors HTTP—confirm ABAP Type 3 RFC pattern separately for ECC/S/4.\n- KBA 2907683 — Connector not defined in grfncciconnector table: https://userapps.support.sap.com/sap/support/knowledge/en/2907683 — Cited in project knowledge for risk-analysis failure when connector registration is incomplete; confirm article body on support portal for the landscape release.\n\n## SAPSUP-004: Which access does the GRC connector communication user need, and why must it be least-privileged?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** design  \n**Verification:** needs_release_or_landscape_verification\n\n**Answer:** The connector communication user is a standing privileged technical identity, so I size it to enabled functions only. For synchronization and risk analysis I grant the read and RFC or API authorizations required to extract user, role and authorization data for the connector type. For provisioning I add only the assignment-change authorizations required by the target and the Access Control provisioning framework—never by default copying a broad SAP_ALL-style profile. Trusted RFC designs add S_RFCACL considerations on the accepting system; HTTP connectors follow the target application’s authentication model. I document which Access Control actions the user supports, test positive and negative cases, and review the account in periodic privileged-access reviews. There is no single universal authorization set that fits every ABAP, Portal, LDAP or cloud connector type across 10.x and 12.0.\n\n**Aliases:** GRC connector technical user authorizations; communication user privileges for GRC connector; least privilege GRC RFC user\n\n**Must include:** privileges differ for read versus provisioning; no universal authorization set; privileged-access review; connector-type dependency\n\n**Must not:** claim one SAP-delivered role fits all connectors; recommend SAP_ALL for connector users\n\n**Sources:**\n- Access Control security/authorization guides for plugin and connector users: https://help.sap.com/ — Exact authorization objects and delivered roles vary by Access Control release and target plugin; confirm in the security guide for the installed SP and connector type before quoting object lists.\n\n## SAPSUP-005: How do you distinguish connector connectivity failures from synchronization, risk-analysis and provisioning failures?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** diagnosis  \n**Verification:** internally_reviewed\n\n**Answer:** I isolate the failing layer with evidence. Connectivity failures show destination or handshake errors—SM59 or HTTP test failures, certificate or network issues—before any meaningful GRC repository update. Synchronization failures occur when the destination works but user/role/authorization extract jobs fail, partial-commit, or filter incorrectly; SM37 or job logs and sample reconciliations prove that. Risk-analysis failures with a healthy sync point to ruleset, connector-group action mapping, inactive groups or missing connector registration for analysis. Provisioning failures after MSMP approval point to PROV mapping, provisioning logs, target permissions or an IDM-mediated path—not to ARA. I correct the failing layer only, then retest that layer before declaring the connector healthy end to end.\n\n**Aliases:** connector connectivity versus sync versus provisioning failure; diagnose GRC connector vs ARA vs ARM provisioning\n\n**Must include:** layered isolation; destination versus sync versus ARA versus provisioning; approval is not provisioning\n\n**Must not:** treating MSMP path defects as connector ping failures; blaming ARA ruleset for SM59 failures\n\n## SAPSUP-006: How do you test a connector end to end after initial implementation or a GRC upgrade?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** testing  \n**Verification:** internally_reviewed\n\n**Answer:** After implementation or an Access Control 10.x-to-12.x upgrade I run a regression pack per connector. I retest the technical destination, confirm Integration Framework registration and active connector-group action mapping, then synchronize a controlled population and reconcile counts plus named sample users and roles to the target. I execute ARA for a known conflict fixture and a known clean fixture so risk results prove data completeness, not only job success. If provisioning is in scope I submit a representative access request through ARM, confirm MSMP completion, then verify the target assignment and a failed-permission negative case. For IDM or IAG Bridge landscapes I validate the mediated path explicitly. I retain destination screenshots or logs, sync reconciliations, ARA evidence and provisioning evidence as the go/no-go pack.\n\n**Aliases:** end to end GRC connector test; validate connectors after GRC upgrade; GRC connector regression test\n\n**Must include:** destination registration mapping; reconcile samples; ARA known conflict and clean; provisioning separate if in scope; evidence pack\n\n**Must not:** job green status alone as proof of data completeness\n\n## SAPSUP-007: How does GRC connector and provisioning architecture differ for direct ABAP provisioning versus SAP IDM or non-ABAP integration?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** architecture  \n**Verification:** internally_reviewed_with_help_portal_references\n\n**Answer:** Direct ABAP provisioning uses an Access Control connector path where, after ARM approval, the provisioning framework assigns roles on the ABAP target through the configured PROV scenario and plugin authorizations. SAP IDM-centric landscapes often keep Access Control for risk and approval while identity provisioning to some targets is owned by IDM; in that case I validate the GRC-to-IDM handoff and IDM-to-target connectors rather than assuming GRC writes every assignment. Non-ABAP targets use the connection type and application type documented for that system—HTTP or other Integration Framework types—not a single generic REST connector for every cloud product. IAG Bridge adds another pattern where cloud risk or request handling may involve IAG while Access Control remains the on-premise engine. I always draw the ownership diagram before testing so failures are attributed to the correct product plane.\n\n**Aliases:** GRC versus SAP IDM provisioning connectors; direct ABAP provisioning vs IDM; non-ABAP GRC connector architecture\n\n**Must include:** direct ABAP PROV path; IDM-mediated ownership; connector type is product-specific; IAG Bridge as separate pattern\n\n**Must not:** all non-SAP systems use one web-service connector; IAG replaces Access Control MSMP for on-premise ABAP\n\n**Sources:**\n- AC 12.0 IAG Bridge Integration Guide: https://help.sap.com/doc/4835e84042834e6c96bfa35f5d7609aa/1902/en-US/AC%20to%20IAG%20Bridge_Integration.pdf — Shows cloud bridge connectors as a distinct architecture from direct ABAP RFC provisioning.\n\n## SAPSUP-008: What would you check if a connector test succeeds but user or role data or ARA results are incomplete?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** diagnosis  \n**Verification:** internally_reviewed_with_help_portal_references\n\n**Answer:** A successful destination test only proves reachability. I next check whether the connector is registered and linked to the AUTH or analysis scenarios, whether the connector group is active, and whether action mapping includes role risk analysis for that group. I inspect synchronization job selection, filters, client and system mapping, and compare repository counts to SUIM or target reports for a sample. Incomplete ARA with full sync points to ruleset scope, exclusions, analysis parameters or stale batches. I rerun a known-conflict fixture after correcting registration or sync scope. I do not widen the communication user until the configuration gap is ruled out.\n\n**Aliases:** connector test OK incomplete ARA data; RFC works but GRC sync incomplete; successful connector ping stale risk results\n\n**Must include:** ping is not registration; scenario link and active group; reconcile counts and samples; known-conflict fixture\n\n**Must not:** immediate privilege escalation of the technical user as first step\n\n**Sources:**\n- KBA 2907683 — Connector not defined in grfncciconnector table: https://userapps.support.sap.com/sap/support/knowledge/en/2907683 — Illustrates analysis failure modes when connector registration is incomplete despite technical connectivity; confirm on support portal.\n\n## SAPSUP-009: How would you plan connector and integration validation in an ECC-to-S/4HANA migration?\n\n**Domain:** GRC Access Control / Migration  \n**Task:** migration  \n**Verification:** internally_reviewed\n\n**Answer:** I treat connectors as a cutover-critical workstream alongside roles and rulesets. Before conversion I baseline ECC connector inventory, scenarios, technical users, sync jobs and ARA fixtures. I assess whether targets remain ABAP RFC, change host or SID, or require new S/4 Fiori/OData-related authorization data for analysis. In the S/4 quality system I rebuild or retarget destinations, re-register Integration Framework entries, remap connector groups and actions, and update ruleset functions for replaced transactions and services. Validation includes destination tests, full or delta sync reconciliation, ARA completeness against known fixtures, ARM provisioning samples if in scope, and freeze criteria before Production cutover. Rollback includes restoring prior destinations and proving emergency access still works. Product-specific work is Access Control Integration Framework; S/4 role redesign and IAG cloud targets are parallel tracks, not substitutes.\n\n**Aliases:** GRC connector validation ECC to S4 migration; Access Control connectors during S/4 conversion; migrate GRC connectors to S/4HANA\n\n**Must include:** baseline before conversion; retarget register remap; ruleset and sync together; ARA completeness not only job success; cutover freeze and rollback\n\n**Must not:** assuming ECC connectors work unchanged on S/4; skipping provisioning tests when PROV remains in scope\n\n## SAPSUP-010: What evidence would you retain for connector setup, sync correctness, provisioning and audit?\n\n**Domain:** GRC Access Control / Connectors  \n**Task:** evidence  \n**Verification:** internally_reviewed\n\n**Answer:** I retain a controlled evidence pack: connector inventory with system ID, connection type, scenarios and owners; destination test results; Integration Framework and Access Control mapping screenshots or exports; technical-user ID with least-privilege justification and review date; synchronization reconciliations with counts and named samples; ARA results for known conflict and clean fixtures with ruleset version; provisioning request IDs, MSMP completion, target assignment proof and negative tests when PROV is enabled; and incident or freeze records for cutover.
